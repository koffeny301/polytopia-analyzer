# Принцип работы polytopia-match-analyzer

Документ объясняет, как программа устроена и почему именно так.
Краткая справка по командам — в [README.md](README.md).

## 1. Общая схема

```
 ссылка на матч                игра (Steam/мобильная)            данные матча
┌──────────────────┐   open   ┌──────────────────────┐  вручную ┌──────────────┐
│ share.polytopia. │ ───────► │ реплей матча         │ ───────► │ match.csv /  │
│ io/g/<uuid>      │  (deep-  │ (просмотр ходов,     │ (шаблон  │ match.json   │
└──────────────────┘  link)   │  счёта, боёв)        │ template)└──────┬───────┘
                              └──────────────────────┘                 │ analyze
                                                                       ▼
                                                        ┌──────────────────────────┐
                                                        │ HTML-отчёт + сводка      │
                                                        │ (графики plotly.js,      │
                                                        │  таблица, награды)       │
                                                        └──────────────────────────┘
```

Ключевое ограничение, определившее архитектуру: **ссылка на матч не содержит
данных**. Страница `https://share.polytopia.io/g/<uuid>` — это только
страница-переключатель с deep-link'ами (`polytopia://opengame?id=...`,
`steam://run/874390//opengame?id=...`). Сам матч хранится на серверах
Midjiwan и загружается исключительно игровым клиентом; публичного API нет.

Поэтому программа:

1. использует ссылку ровно для того, на что она способна — извлекает UUID и
   открывает реплей в игре (модуль `links.py`, команда `open`);
2. принимает данные матча из **собственного формата** (CSV/JSON), который
   заполняется вручную по ходу просмотра реплея (команда `template`);
3. не привязана к источнику данных: формат матча — внутреннее представление,
   и любой будущий автоматический источник (PolyMod-экспорт, парсер
   `.state`-сейвов, OCR экрана) подключается как новый «адаптер входа»,
   не затрагивая анализ и отчёты.

## 2. Конвейер обработки (команда `analyze`)

```
файл (.csv/.json)
   │  storage.load_match()          парсинг + приведение типов
   ▼
Match (модель памяти)               models.Match.validate() — целостность
   │  analysis.*                    производная статистика
   ▼
PlayerStats / standings / rank_history / awards
   │  report.build_report()         фигуры plotly + HTML-вёрстка
   ▼
один самодостаточный .html файл  +  текстовая сводка в консоль (cli.py)
```

Каждый этап зависит только от предыдущего: `storage` не знает про графики,
`analysis` не знает про HTML, `report` не читает файлы. Это позволяет
тестировать этапы независимо и заменить любой из них (например, вывести
отчёт в PNG) без переписывания остальных.

## 3. Модель данных (`models.py`)

Матч — это три сущности:

- **MatchMeta** — метаданные: название, дата, режим, карта, ссылка на реплей,
  лимит ходов, заметки;
- **Player** — игрок: имя, племя, цвет на графиках, признак «человек»;
- **TurnRecord** — показатели одного игрока за один ход.

Главное соглашение модели — два типа метрик в `TurnRecord`:

| Тип | Поля | Смысл |
|---|---|---|
| **снимок** (snapshot) | `score`, `income`, `army`, `cities` | значение *на конец хода* |
| **прирост** (delta) | `kills`, `losses`, `captured`, `lost_cities`, `damage` | сколько произошло *за этот ход* |

Из этого следуют все правила анализа: снимки рисуются как есть и
усредняются, приросты — суммируются (итоги матча) и накапливаются
(кумулятивные графики). Перепутать их нельзя: списки `SNAPSHOT_FIELDS` и
`DELTA_FIELDS` объявлены в модуле, и `analysis.py` опирается на них, а не
на имена полей.

Данные разрежены легально: ходы можно пропускать (не всё видно в реплее),
колонки — не заполнять. `Match.validate()` проверяет только целостность:
игроки уникальны, записи ссылаются на известных игроков, нет дублей
«ход+игрок», номера ходов неотрицательны.

## 4. Хранение и парсинг (`storage.py`)

Два равноправных формата с точным round-trip'ом (CSV → JSON → CSV даёт те же
данные — это покрыто тестами).

**CSV** — основной формат ручного ввода. Метаданные и игроки живут в
комментариях, чтобы файл оставался обычной таблицей (открывается в LibreOffice
/ Excel / Obsidian):

```csv
# title: Матч с друзьями            ← # key: value → поле MatchMeta
# player: koffeny301; Vengir; #e6194B; human   ← имя; племя; цвет; человек
turn,player,score,income,...
```

**JSON** — машинный формат: `{"meta": {...}, "players": [...], "turns": [...]}`.

Принципы парсинга:

- **строгая схема, мягкие значения**: неизвестные поля/колонки — ошибка
  (защита от опечаток), а пустые ячейки и отсутствующие колонки метрик —
  законный ноль;
- **полностью пустые записи игнорируются**: строка CSV (или JSON-запись),
  где не заполнена ни одна метрика, не загружается — незаполненные будущие
  ходы шаблона не искажают финальный счёт, прирост и графики. Достаточно
  хотя бы одного значения, чтобы запись считалась заполненной;
- **целые значения пишутся без хвоста `.0`** (`520`, а не `520.0`), поэтому
  round-trip CSV → JSON → CSV побайтово стабилен;
- **приведение типов в одном месте** (`_to_number`): строки, числа, `None`
  приводятся единообразно, десятичная запятая и точка равноправны
  (`4,5` = `4.5`), нечисло — понятная ошибка с именем поля;
- **ошибки с контекстом**: парсер CSV сообщает номер строки;
- файл с неизвестным расширением пробуется сначала как JSON, затем как CSV.

## 5. Ссылки на матч (`links.py`)

Модуль умеет одно: извлекать UUID матча из любого формата
(`https://share.polytopia.io/g/<uuid>`, `polytopia://opengame?id=<uuid>`,
`steam://run/874390//opengame?id=<uuid>`, голый UUID в любом регистре) и
строить обратно три вида ссылок. Команда CLI `open` печатает их, а с флагом
`--launch` запускает реплей в Steam через системный opener
(`xdg-open`/`open`/`cmd start` — по платформе).

## 6. Анализ (`analysis.py`)

Все производные величины считаются из записей матча, ничего не хранится:

- **PlayerStats** — итоги игрока: финальный и пиковый счёт, средний доход,
  пики армии/городов, суммы приростов (kills, losses, captured,
  lost_cities, damage), прирост счёта за матч, «лучший ход» (максимальная
  разница счёта между соседними записями);
- **K/D** — `kills / losses`; если потерь не было, K/D равен числу убийств
  (ноль при нулевых убийствах) — чтобы не показывать бесконечность;
- **standings** — сортировка по финальному счёту (при равенстве — по имени);
- **rank_history** — место игрока на каждом зафиксированном ходу. Принцип:
  между записями используется **последний известный счёт** игрока; ещё ни
  разу не записанные игроки идут в конец. Так разреженные данные не ломают
  хронологию;
- **leader_changes** — смена обладателя 1-го места по ходам (первая запись —
  первый лидер);
- **cumulative_series** — накопительный итог любой дельта-метрики: сумма
  приростов по записям игрока в порядке ходов;
- **awards** — номинации: «Воин» (максимум убийств), «Экономист» (средний
  доход), «Завоеватель» (захваты), «Снайпер» (лучший K/D среди убивавших),
  «Стратег» (прирост счёта). Вручаются только за ненулевые достижения.

Цвета игроков: явный цвет из данных, иначе палитра из 10 различимых цветов
по порядку в списке игроков (`DEFAULT_COLORS`) — поэтому цвета стабильны
между таблицей, графиками и наградами.

## 7. Отчёт (`report.py`)

Отчёт — **один HTML-файл без внешних зависимостей**:

1. **Фигуры как данные.** Каждый график (8 штук: счёт, доход, города, армия,
   места, кумулятивные kills/losses, боевые итоги) собирается в Python-словарь
   формата plotly.js (`{"data": [...], "layout": {...}}`), затем весь набор
   сериализуется в JSON и уходит в страницу одним блоком; отрисовка —
   цикл `Plotly.newPlot(id, fig.data, fig.layout, {responsive: true})`.
   Никакой серверной части и сборки фронтенда нет.
2. **plotly.js встроен в файл** из `polytopia_analyzer/assets/plotly-basic.min.js`
   (~1 МБ) — отчёт открывается офлайн и пересылается как есть. Флаг CLI
   `--cdn` заменяет встроенный JS ссылкой на CDN (файл становится маленьким,
   но требует интернет).
3. **Безопасный HTML.** Все пользовательские строки (имена, названия)
   проходят `html.escape`. JSON с данными фигур дополнительно экранирует
   `<`, `>`, `&` в `\u003c` и т.п. — иначе имя игрока вроде
   `</script><script>...` могло бы закрыть скриптовый блок и выполнить
   произвольный код. JSON остаётся валидным: JavaScript сам раскрывает
   `\uXXXX` в строковых литералах.
4. **Вёрстка** — строковый шаблон (CSS как обычная строка, динамические
   блоки через f-строки), тёмная «цивилизационная» тема: тёмно-синий фон,
   золотые акценты, баннер победителя, таблица итогов, секции графиков,
   карточки наград, хронология лидерства.

## 8. CLI (`cli.py`)

Принцип: `main(argv=None) -> int` — функцию можно вызывать из тестов
in-process, а консольная точка входа объявлена в `pyproject.toml`
(`polytopia-analyzer = polytopia_analyzer.cli:main`). Подкоманды:

| Команда | Действие |
|---|---|
| `analyze` | загрузка → анализ → отчёт + сводка в консоль; вывод по умолчанию `<вход>_report.html` рядом с входным файлом |
| `template` | генерация пустого CSV на N ходов × M игроков с подсказками по колонкам |
| `open` | ссылка → UUID → три deep-link'а; `--launch` запускает Steam |
| `convert` | CSV ↔ JSON через модель памяти (проверка формата заодно) |

Ожидаемые ошибки (нет файла, битые данные, неверная ссылка) перехватываются
в `main` и возвращают код 1 с сообщением на русском — без трейсбеков.

## 9. Тестирование

Разработка велась по TDD (сначала падающий тест, затем минимальная
реализация): 43 теста pytest покрывают round-trip'ы форматов, валидацию,
все формулы анализа, экранирование и встраивание JS в отчёте, каждую команду
CLI. Конфигурация `[tool.pytest.ini_options] pythonpath = ["."]` позволяет
тестам импортировать пакет без установки. Визуальная корректность отчёта
проверялась отдельно в реальном браузере (все 8 графиков рендерятся).

Запуск: `.venv/bin/pytest -q`

## 10. Точки расширения

Формат матча — граница, к которой всё сходится, поэтому новые источники
данных добавляются адаптерами *до* модели:

- **PolyMod-экспорт** (Steam): мод сериализует состояние игры в JSON —
  конвертер `mod_replay_*.json → Match` даст полностью автоматический
  pipeline «ссылка → реплей → отчёт»;
- **парсер `.state`-сейвов** одиночной игры (LZ4 + бинарный формат, см.
  PolytopiaSaveEditor/PolytopiaWorld);
- **OCR** экрана счёта из игры/скриншотов — самый хрупкий вариант, последний
  по приоритету.

Новые виды отчётов (PNG, Markdown) добавляются параллельно `report.py` —
`analysis.py` уже отдаёт готовые структуры данных.
