# План v0.2: нативный импорт через ссылку (PolyMod) + точный ручной экспорт

Статус: СОГЛАСУЕТСЯ. Код по этому плану ещё не пишется.
Решения пользователя: платформы — Windows и Linux/Proton; старт — параллельно
спайк PolyMod (M0) и валидация (M1); «точный ручной экспорт» = строгий ввод
в веб-редакторе + OCR скриншотов + строгая CSV-спецификация с общей валидацией.

## 0. Архитектурный принцип

Три входных адаптера сводятся к единой модели Match, затем общая валидация,
затем существующие отчёт и веб-UI. Ядро (models/storage/analysis/report)
меняется минимально.

```
 PolyMod-экспорт ─┐
 Скриншот (OCR)  ─┼→ importers/* → Match → validation → report / web-UI
 Ручной ввод     ─┘                            ↑
                                    warnings подсвечиваются в UI
```

Осознанно вне объёма:
- скрапинг мультиплеерного бэкенда Midjiwan (нет публичного API, политика
  разработчиков против — ссылка share.polytopia.io остаётся только deep-link'ом);
- полная автоматизация просмотра реплея кликами + чтением пикселей (хрупко,
  см. заброшенный PolyAnalytics);
- OCR-2 (походовое распознавание с автопривязкой) — отдельный план после
  практики с OCR-1.

## 1. Изменение модели данных (единственное в ядре)

MatchMeta — два новых необязательных поля:

| Поле | Значения | Смысл |
|---|---|---|
| `source` | `manual` (по умолчанию) / `polymod` / `ocr` | происхождение данных |
| `verified` | ISO-дата или пусто | пользователь принял предупреждения валидации |

- `META_FIELDS` расширяется; старые CSV/JSON остаются валидными.
- В CSV: комментарий `# source: polymod`.
- Отчёт: бейдж источника рядом с метой; при `source=polymod` сноска
  «урон недоступен при автоизвлечении».

## 2. Трек A — M0: спайк PolyMod (нужно участие пользователя)

Цель: один реальный файл экспорта + вердикт по платформе.

- Кандидат №1: **polyfish-mod** (BepInEx-плагин; при просмотре реплея
  сериализует состояния игры, работает и с мультиплеерными реплеями по ссылке).
- Кандидат №2: **polytopia-singleplayer-library v0.1.7** (проверенная связка:
  игра 2.17.3.16375 + PolyMod 1.2.18, Windows Steam; только одиночные реплеи —
  запасной вариант для проверки формата).
- Артефакты агента: `docs/polymod-setup.md` (установка на Windows и Linux/Proton:
  BepInEx в префикс через protontricks, override winhttp) + скрипт-диагностика
  (проверка логов мода, поиск файлов экспорта).
- Действия пользователя: установить мод, открыть реплей по ссылке,
  досмотреть, сообщить путь к экспортному JSON.
- Критерий успеха: файл получен; зафиксирован маппинг полей (присутствуют ли
  score/income/units/cities с владельцами).
- Риск-решение: если под Proton мод не загружается — автоимпорт выполняется
  на Windows-машине, файл копируется в `data/inbox/`; ручной трек не страдает.

## 3. Трек B — M1: валидация

Новый файл `polytopia_analyzer/validation.py`.

Ошибки (блокируют сохранение и анализ):

| Код | Проверка |
|---|---|
| E_UNKNOWN_PLAYER | запись ссылается на неизвестного игрока |
| E_DUPLICATE | дубль «ход + игрок» |
| E_NEGATIVE_TURN | номер хода < 0 |
| E_NEGATIVE | отрицательное значение метрики (все метрики ≥ 0) |
| E_DUP_NAME | неуникальные имена игроков |

Предупреждения (подсветка, не блокируют):

| Код | Проверка |
|---|---|
| W_CITY_BALANCE | для соседних записей: cities(t) − cities(t−1) ≠ captured(t) − lost_cities(t); проверяется только при всех четырёх заполненных значениях |
| W_KILL_NO_DAMAGE | kills > 0, но damage = 0 (когда damage заполнен) |
| W_SCORE_DROP_UNEXPLAINED | score(t) < score(t−1) при нулевых losses и lost_cities за ход t |
| W_INCOME_SPIKE | income(t) > 2·income(t−1) + 3 |
| W_ARMY_SPIKE | прирост армии за ход больше дохода за этот ход |
| W_KILLS_APPROX | (импортёр) kills/losses выведены по исчезновению id юнитов, события «роспуск/смерть» в экспорте отсутствуют |

Инфо:

| Код | Проверка |
|---|---|
| I_GAP | пропущенные ходы между min и max записанным (списком) |
| I_COMPLETENESS | % заполненных ячеек по каждому игроку |
| I_SCORE_JUMP | скачок счёта > 5× медианного прироста и > 500 очков |

Элемент выдачи: `{code, severity, turn, player, metric, message}`.

Интеграция:
- API: `POST /api/validate {match}` → `{ok, errors, warnings, info, completeness}`.
- `POST /api/matches/*` перед сохранением прогоняет валидацию:
  errors → 400 со списком; warnings не блокируют.
- CLI: `validate <файл>` (код возврата 1 при errors); `analyze` печатает
  сводку предупреждений перед построением.
- Веб-UI: панель «Проверка данных»; запуск при загрузке матча и debounce
  600 мс после правок; клик по предупреждению → скролл к ячейке + класс
  `.warn-cell`; кнопка «Принять предупреждения» → `meta.verified`.

## 4. M2: мастер ввода по ходам (веб-UI)

- Переключатель «Таблица / Мастер» в тулбаре сетки.
- Карточка одного хода: все игроки × 9 полей; Enter — следующее поле,
  Ctrl+Enter — следующий ход, Esc — выход; прогресс «Ход 12/30».
- Данные пишутся в тот же recMap (полная совместимость с таблицей).
- Справочник метрик: расширенные тултипы + `docs/metrics.md` (определение
  метрики и где именно смотреть её в игре).

## 5. M3: импортёр PolyMod (точный маппинг — после образца M0)

- `importers/polymod.py` — парсинг экспорта.
- `importers/differ.py` — производные метрики из разницы снапшотов:
  - score/income/army/cities — из снапшота; при отсутствии готового score —
    расчёт по формулам вики (`importers/score_calc.py`: города 100+50×(уровень−1),
    территория 20/тайл, юниты 5×стоимость, технологии 100/тир, храмы,
    монументы 400, парки 250);
  - captured/lost_cities — смена владельца города;
  - kills/losses — исчезновение юнитов по id (роспуск vs смерть — по наличию
    событий; иначе W_KILLS_APPROX);
  - damage — недоступно, поле НЕ заполняется (не ноль).
- CLI: `import <файл> [-o match.json]` (auto | polymod | csv | json);
  `watch-inbox [--dir DIR] [--interval 2]` — поллинг папки (stdlib),
  автоимпорт новых файлов в `data/inbox/` с `meta.source=polymod`.
- API: `POST /api/import {format, content}` → `{match, warnings}`;
  `GET /api/inbox`; `POST /api/inbox/<имя>/accept`.
- Веб-UI: секция «Входящие (автоимпорт)» — список, «Открыть»/«Удалить»;
  бейдж источника на карточках матчей и в шапке редактора.
- Тесты: синтетическая фикстура-экспорт (по образцу), формулы differ/score_calc,
  watch-inbox на tmp_path.

## 6. M4: OCR-1 — точный экспорт из скриншота финального табло

- Зависимости (опциональный extra): `ocr = ["pillow>=10", "pytesseract>=0.3.10"]`;
  системный tesseract (Arch: `sudo pacman -S tesseract`; Windows: установщик
  UB-Mannheim). При отсутствии — ошибка с командой установки.
- API: `POST /api/ocr {image_b64}` → `{numbers: [{value,x,y,w,h,conf}], width, height}`
  (pytesseract image_to_data, whitelist цифр).
- Веб-UI: «Загрузить скриншот счёта» → картинка с кликабельными найденными
  числами → таблица назначения (число → игрок + метрика + ход, по умолчанию
  score и финальный ход) → предпросмотр записей → валидация → сохранение
  с `meta.source=ocr`.
- Принцип: OCR только находит числа, привязывает их человек — ошибки
  распознавания не попадают в данные молча.

## 9. Порядок работ и критерии приёмки

| Веха | Содержание | Критерий приёмки |
|---|---|---|
| M1 | validation.py + тесты → API → UI-панель → CLI | на демо-матче с намеренной ошибкой UI показывает W_CITY_BALANCE на нужной ячейке; сохранение с E_NEGATIVE отклоняется 400 |
