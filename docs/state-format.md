# Формат одиночных сейвов Polytopia (`.state`, v124)

Как анализатор читает сейвы одиночной игры и откуда взялось знание формата.
Реализация: `polytopia_analyzer/importers/state.py` (чистый stdlib, свой
LZ4-декодер). Фикстура: `tests/fixtures/singleplayer-v124.state` — настоящий
сейв игры 2.18 (Linux, Steam), свежесозданная партия на ходе 0.

## Где лежит сейв

- Linux: `~/.config/unity3d/Midjiwan/Polytopia/<uuid>/Data/Singleplayer/<uuid>.state`
- Windows: `%USERPROFILE%\AppData\LocalLow\Midjiwan\Polytopia\<uuid>\Data\Singleplayer\`
- Override для анализатора: `POLYTOPIA_SAVES_DIR`

Игра держит один сейв одиночной партии и перезаписывает его; при старте новой
партии старый удаляется. Сейвы мультиплеера (`Data/Multiplayer/`) в этой версии
игры — 6-байтные заглушки, не разбираются.

## Кредиты

Формат reverse-engineered Samuel Yuan (MIT License), проекты:
`PolytopiaSaveEditor`, `polytopiamapmodelgo`, `PolytopiaWorld`,
`PolytopiaMapImage`; конвертер сейвов также используется в `NeoLorenzo/PolyVision`.
Раскладка v122 взята из `polytopiamapmodelgo`. Отличия версии **v124**
(игра 2.18, ноябрь 2026) найдены эмпирически на живом сейве этим проектом и
зафиксированы тестами `tests/test_state_import.py`. Community-инструменты
(Go-библиотека v122) сейв v124 прочитать уже не могут — рассинхрон на записях
игроков.

## Конверт и LZ4

```
[0]      флаг: 0x80 → размер diff 2 байта, 0xC0 → 4 байта (биты 6-7)
[1..]    diff = len(декомпрессированного) − len(LZ4-блока), little-endian
[off..]  сырой LZ4-блок (без фрейма: lz4 block format)
```

Размер результата = `len(файла) − off + diff`; декодер обязан сойтись байт в
байт (контроль размера — первый оракул целостности).

## Раскладка файла

```
[u32 версия файла = 124]
[НАЧАЛЬНОЕ состояние]      ← генерация мира (ход 0, до действий игрока)
[непрозрачный разделитель]  ← v122: 3 байта; v124: 11 байт (3 + u32 0 + u32 константа сейва)
[ТЕКУЩЕЕ состояние]
[разделитель 2 байта]
[u16 numActions][действия…]
[хвост]                     ← v124: ~10 байт, содержит ту же константу сейва
```

Каждое состояние = `[u32 версия][заголовок][тайлы W×H][игроки]`. В v122-описании
второй u32 первого состояния принимался за «Version2» — на самом деле это
версия самого начального состояния (в v124 каждая секция несёт свою версию, и
TotalActions текущего состояния подтверждается numActions секции действий).

### Тайлы (W×H, построчно: row=y, col=x)

Фиксированная часть 24 байта: `x u32, y u32, terrain u16, climate u16,
altitude i16, owner u8, capital u8, capital_x i32, capital_y i32`, затем
переменные секции: ресурс (флаг u8 [+u16 тип]), улучшение (флаг u8 [+u16 тип]
+ ImprovementData), юнит (флаг u8 + UnitData 42 байта [+ пассажир]), видимость
(u8 len + байты), дорога/водный путь (u8×2), скин (u16), unknown (2 байта),
flooded (version ≥ 105: u8 [+u32]).

ImprovementData: `level u16, founded_turn u16, current_pop i16, total_pop u16,
production i16, base_score i16, border_size i16, upgrade_count i16,
connected_capital u8, has_city_name u8 [+varstr], founded_tribe u8,
city_rewards u16[]…, rebellion_flag u16 [+2 байта если ≠0]`.
Тип улучшения 1 = город (владелец — owner тайла; owner 0 = нейтральные деревни).

UnitData (42 байта): `id u32, owner u8, type u16, follower_id u32, leader_id u32,
x i32, y i32, home_x i32, home_y i32, health u16 (÷10 = HP в игре),
promotion u16, experience u16, moved u8, attacked u8, flipped u8,
created_turn u16`.

### Игроки

`u16 count`, затем записи: `id u8, [v122+: возможный маркер 0xff], name varstr,
account_id varstr, auto_play u8, start_x i32, start_y i32, tribe u16,
unknown u8, handicap u32, [version < 114: aggressions], currency u32 (звёзды),
score u32, unknown u32, num_cities u16, tech u16[], encountered u8[],
tasks (тип i16: 1/5 → 6 байт буфер, 2..8 → 2 байта), kills i32, losses i32,
tribes_destroyed i32, override_color 4Б, override_tribe u8,
unique_improvements u16[], diplomacy (23Б/запись)[], diplomacy_messages (2Б)[],
destroyed_by_tribe u8, destroyed_turn u32, unknown 4Б, end_score i32,
skin u16, unknown 4Б` — и **новый в v124 контрольный байт == tribe** (см. ниже).

Счётчики kills/losses/tribes_destroyed накопительные (как в снимках шима).
Варвары: id 255, tribe 1, имя «Nature».

### Действия

`u16 numActions`, затем `[u16 тип][полезная нагрузка]`. Размеры нагрузок
(v122-таблица, для v124 сверена по суммарному потреблению): 1:11, 2:21, 3:9,
4:9, 5:11, 6:21, **7:13 (захват города: player u8, unit_id u32, x u32, y u32)**,
8:3 (исследование), 9:9, 11:11, 13:9, 14:9, **15:1 (конец хода; player==255 →
новый ход)**, 16:11, 17:9, 18:9, 20:1, 21:9, 24:9, 25:9, 27:10, 28:3, 29:10,
30:10. История действий позволяет восстановить захваты городов по ходам
(задача M7.2 — нужен сейв средней партии для проверки).

## Отличия v124 от опубликованного v122

1. **Контрольный байт игрока**: после каждой записи игрока стоит байт, равный
   `tribe & 0xFF` (проверено 3/3 на живом сейве: 7→7, 13→13, 1→1). Парсер
   требует совпадения — иначе ошибка «Контрольный байт племени не совпал».
2. **Каждая секция состояния начинается со своей версии (u32)**; то, что
   v122-библиотека звала «Version2» первого заголовка, — версия начального
   состояния. Фиксированная часть заголовка текущей секции поэтому на 4 байта
   короче «двухверсионного» первого.
3. **Непрозрачные вставки**: между секциями и в конце файла появились доп.
   байты, включающие константу сейва (в образце `a6 59 b4 07`, встречается
   дважды; смысл не установлен — вероятно, метка времени/идентификатор сеанса).
   Парсер не интерпретирует их, а находит границы сканом + оракулами.

## Оракулы целостности (fail-closed)

Любое рассогласование — ошибка, молчаливых пропусков нет:

- точный размер LZ4-декомпрессии;
- версии файла и обеих секций ∈ `SUPPORTED_FILE_VERSIONS` (сейчас {124});
- координаты каждого тайла `(x,y)==(col,row)` — главный оракул раскладки;
- контрольный байт игрока == tribe;
- numActions == total_actions текущего заголовка;
- границы секций ищутся сканом с полной перепроверкой (заголовок → тайлы →
  игроки), а не жёсткими длинами разделителей.

## Что переносится в модель Match

| Метрика | Источник | Заполняется |
|---|---|---|
| score | score игрока (точное) | да |
| cities | num_cities | да |
| army | подсчёт юнитов тайлов по owner | да |
| kills / losses | накопительные → прирост разностью с начальным состоянием (относится к последнему записанному ходу) | да |
| income, captured, lost_cities, damage | в сейве нет в готовом виде (captured выводится из действий в M7.2) | нет (пусто, не ноль) |

Записи: ход 0 (начальное состояние, если партия шла) и текущий ход.
`meta.source = "state"`, `turn_limit` — из заголовка, `date` — mtime файла,
`is_human` = NOT auto_play. Племена — общая таблица `TRIBE_NAMES`
(1=Nature, 4=Bardur, 15=Zebasi, 16=Polaris; непроверенные id → `Tribe<n>`).

## Открытые вопросы (проверить на сейве средней партии)

- В свежем сейве (ход 0) юнитов нет вовсе: стартовые юниты ещё не заспавнены.
  Косвенное подтверждение: счёт 505 = 405 (столица+территория+туман) + 100
  (технология), без +5 за юнита. Парсинг UnitData на живых данных не проверен.
- Семантика действия типа 20 (в образце единственное, payload `01`).
- Назначение константы `a6 59 b4 07` и точная структура разделителей/хвоста.
- tribe id 7 и 13 — до сверки с игрой отображаются как `Tribe7`/`Tribe13`.
- `max_unit_id` текущего заголовка = 0 при прочтенном по no-seed-варианту 2 —
  поле не используется, неоднозначность не критична.
- Когда именно игра перезаписывает сейв (каждый ход или только при выходе) —
  от этого зависит будущий режим watch (M7.2).

## Проверка новой версии игры

При обновлении игры парсер обязан отказаться от неизвестной версии
(«Неподдерживаемая версия формата .state: N»). Порядок легализации новой
версии: достать живой сейв → прогнать оракулы → найти расхождения дампом
байтов (методика: `docs/state-format.md` + история в git) → добавить версию в
`SUPPORTED_FILE_VERSIONS` вместе с тестами на новом фикстуре.
