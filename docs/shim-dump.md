# Веха 6.2 — дамп живого состояния матча

Дата: 2026-11-13. Стенд: Polytopia 2.18.0.16751, нативная Linux-сборка, Steam-запуск,
реплей `share.polytopia.io/g/35b44c27-a0a2-4f52-3290-08df4019957a` (Timeless Battles).

Итог: **состояние читается целиком.** За один проход реплея записано **13 снимков
(ходы 0–12)**: счёт, звёзды, города, убийства, потери, племя и факт сдачи по каждому игроку.

## Как устроено

```
Steam (deep-link opengame?id=…) → игра → LD_PRELOAD: libpolyread_dump.so
   поток в игре: найти GameState → раз в опрос прочитать PlayerStates
   → snapshot-<ход>.json + latest.json в ~/.local/share/polytopia-analyzer/inbox/
```

Путь к состоянию (проверено):

```
GameManager.instance            статическое поле, класс GameManager
  .client                       ClientBase (в реплее — ReplayClient)
    .currentGameState           GameState      ← то, что нужно
      .<CurrentTurn>            uint32 — номер хода
      .<PlayerStates>           List<PlayerState>
        PlayerState.score       uint32
        PlayerState.currency    int32 (звёзды)
        PlayerState.cities      int32
        PlayerState.kills / casualities / resignedTurn / tribe / <UserName>
```

Статические поля типа `GameState` (`GameManager.mockedGameState` и др.) в матче пустые —
рабочий путь именно через `client`. Поля читаются **по цепочке наследования**: у
`ReplayClient` своих полей нет, всё объявлено в `ClientBase`.

## Снимок хода

Ход фиксируется **в момент смены `CurrentTurn`**, а не в конце хода. Проверено сверкой
с OCR-эталоном: значения, взятые на смене хода, совпадают с тем, что HUD показывает
для этого хода; значения, взятые в конце хода, сдвинуты на один ход.

## Грабли этого этапа (все воспроизведены и обойдены)

1. **Deep-link не работает в ручном запуске.** Ссылка `share.polytopia.io` — это
   `opengame?id=<uuid>`; игра получает её через Steam API (в `cmdline` аргументов нет),
   прямой `./Polytopia.x86_64 'opengame?id=…'` доходит только до экрана `UIDeepLinkData`
   и остаётся в меню. Значит шим обязан грузиться в процесс, запущенный **Steam**.
2. **Правка `LaunchOptions` в `localconfig.vdf` на ходу не действует** — Steam держит
   конфиг в памяти и перезаписывает файл. Для теста обошлись без перезапуска Steam:
   подменили исполняемый файл обёрткой (обратимо, см. ниже).
3. **Обёртка ломает поиск данных Unity.** Движок ищет `<имя-бинарника>_Data` рядом с
   собой: при переименовании в `Polytopia.x86_64.real` нужен симлинк
   `Polytopia.x86_64_Data → Polytopia_Data` (и `.real_Data` тоже — Unity пробует разные
   варианты), иначе `FindDataPath: Player data not found!`.
4. **Защита от падений обязана ставиться до первого чтения.** Первый вариант ставил
   обработчик SIGSEGV только перед циклом монитора; диагностический проход читал
   статическое поле неинициализированного класса по нулевому указателю и уронил игру.
   Теперь `install_guards()` вызывается сразу после резолва API.
5. **Поле ищется по родителям.** `il2cpp_class_get_fields` отдаёт только собственные
   поля класса; без обхода `il2cpp_class_get_parent` состояние не находится.
6. **Снимок берётся на смене хода** (см. выше), иначе числа сдвинуты на ход.

## Установка через строку запуска Steam (веха 6.4)

Подмена бинарника нужна была только для теста. Штатный путь — параметры запуска
игры в Steam:

```bash
polytopia-analyzer install-shim status
polytopia-analyzer install-shim enable --restart-steam
polytopia-analyzer install-shim disable --restart-steam
```

Что делает установщик:

- находит `userdata/<id>/config/localconfig.vdf`, блок приложения `874390`;
- пишет `"LaunchOptions" "POLYREAD_DUMP=<inbox> LD_PRELOAD=<шим> %command%"`,
  сохраняя прежнее значение в своём состоянии (`~/.local/share/polytopia-analyzer/steam-launch.json`)
  и резервную копию конфига (`localconfig.vdf.polyread.bak`);
- **останавливает и запускает Steam** (`--restart-steam`): Steam держит конфиг
  в памяти и перезаписывает файл при выходе, поэтому правка при работающем
  клиенте не действует. Без флага установщик откажется писать;
- откат возвращает прежнее значение (или убирает ключ, если его не было);
  если пользователь успел поменять строку вручную — откат требует `--force`.

Проверено на живой игре (13.11): включение с перезапуском Steam, запуск реплея
по deep-link, шим загрузился **без обёртки** (`LD_PRELOAD` в окружении процесса,
бинарник игры не тронут — md5 `71d3c9d3…`), снято 13 снимков. Сверка с набором
6.2: 11 ходов совпали точно, ход 0 у второго игрока отличается на 10 очков —
снимок первого хода иногда берётся чуть раньше применения дохода. Откат тоже
проверен: параметры запуска очищены, Steam перезапущен.

Ограничения, которые надо помнить:

- `LD_PRELOAD` из строки запуска **заменяет** предзагрузку Steam-оверлея
  (в окружении игры остаётся только шим) — оверлей в игре работать не будет;
- в живом матче дамп включать нельзя (это чтение чужого состояния); фильтр
  «только реплей» — задача до включения по умолчанию;
- `--restart-steam` закрывает клиент Steam: активные загрузки/игры прервутся.

## Как запустить

```bash
make -C shim                                  # libpolyread_probe.so + libpolyread_dump.so
shim/install-wrapper.sh --enable              # временная обёртка в папке игры (обратимо)
xdg-open 'steam://run/874390//opengame?id=<uuid>'
# снимки: ~/.local/share/polytopia-analyzer/inbox/
shim/install-wrapper.sh --restore             # вернуть оригинальный бинарник
```

`install-wrapper.sh --enable` — **резервный** путь (если строку запуска менять нельзя):
кладёт оригинал рядом как `Polytopia.x86_64.real`, создаёт симлинки `*_Data` и обёртку,
которая запускает игру с `LD_PRELOAD`. `--restore` возвращает всё назад и проверяет
контрольную сумму.

## Фильтр «только реплей» (6.6)

Снимки пишутся, **только если клиент игры — реплейный**. Признак берётся из класса
объекта, через который найден `GameState`: в реплее это `ReplayClient`, в живом матче —
`LocalClient`/`RemoteClient`/`HotseatClient`. Проверка стоит перед каждой записью, отказ
выводится в `dump.log` одной строкой:

```
не реплей (клиент «LocalClient») — снимки не пишем; обход для отладки: POLYREAD_DUMP_ALLOW_LIVE=1
```

Логика fail-closed: если класс клиента ещё не определён, снимков тоже нет. Отладочные
переменные: `POLYREAD_DUMP_ALLOW_LIVE=1` (снять фильтр), `POLYREAD_DUMP_REQUIRE=<класс>`
(проверить сам механизм на эталонном реплее).

## Регистрация потока в IL2CPP (обязательно)

Поток шима регистрируется через `il2cpp_thread_attach` сразу после резолва символов
(`POLYREAD_DUMP_NO_ATTACH=1` отключает). Без регистрации чтение метаданных иногда
аллоцирует память, GC игры пытается начать сборку из неизвестного потока и вызывает
`abort` — падает весь процесс:

```
Collecting from unknown thread
Received signal SIGABRT (6) … #16 w_cls_fields … #19 run_dump
```

С регистрацией полный проход реплея (156 с) прошёл без единого падения; проверено дважды.

## Формат снимков v2 (0.6.0): армия, доход, захваты, журнал команд

Разведка пробником (probe2/probe3, полные списки полей) показала, где живут
недостающие метрики:

- **армия** — `GameState.Map.tiles[]` (`TileData`): у каждого тайла есть
  `unit: UnitState` с полем `owner`. Армия = число юнитов игрока на карте;
- **доход** — `TileData.improvement: ImprovementState`, поле `production`
  (UInt16) = звёзды/ход города. Доход игрока = сумма production его городов.
  Сверено с HUD: совпадает; награды руин/городов в него не входят (видны как
  превышение Δstars над доходом);
- **захваты** — дифф владельца городов между снимками. Владелец города =
  `TileData.owner` (владелец тайла): поле `ImprovementState.owner` в реплее
  НЕ заполнено (всегда 0) — это грабли. Сверено с журналом команд: 8/8;
- **журнал команд матча** — `GameManager.client.targetGameState.CommandStack`:
  полный список команд реплея (вычисляется игрой при загрузке, ещё до
  просмотра!). Выгружается один раз в `commands.json`: индекс, класс,
  `PlayerId`, `Type` (у Train/Build/Research/Upgrade). Границы ходов —
  `EndTurnCommand` (по одному на игрока за ход, включая варваров);
- **урон** — ~~надёжного источника нет~~ **сделано в 0.8.0** (см. раздел ниже):
  `AttackAction.Damage` живёт в `currentGameState.ActionStack`, а это ЖИВАЯ
  ОЧЕРЕДЬ анимаций — перехват опросом ловит лишь ~30% боевых действий даже
  при опросе каждые 50 мс (проверено сверкой с цензом `AttackCommand` на двух
  реплеях: 4/16 и 74/243). Урон реконструируется детерминированно:
  `AttackCommand` (uid/координаты) + HP-дельты юнитов между снимками.

Формат `snapshot-<ход>.json` (v2):

```json
{"v": 2, "turn": 12, "actions_total": 9,
 "players": [{"id": 1, "name": "KOF", "tribe": 16, "score": 4485, "end_score": 0,
              "stars": 8, "cities": 7, "kills": 1, "casualties": 2,
              "resigned_turn": -1, "wiped": false, "army": 15, "production": 19}],
 "cities": [[x, y, tile_owner, imp_owner, type, level, production], ...],
 "units": [[id, owner, health, type, x, y], ...],
 "events": [{"t": "income", "p": 1, "amt": 2}, ...]}
```

`events` — диагностика (очередь анимаций ненадёжна, импортёр их игнорирует);
`cities`/`units` — полные списки на момент смены хода. Импортёр
(`importers/shim.py`) из v2 заполняет метрики: score, cities, kills, losses
(дельты), army, income (=production), captured/lost_cities (дифф городов),
damage (журнал команд + HP-дельты, см. ниже). Снимки v1 импортируются
по-прежнему (4 метрики).

Реплей проигрывается автоматически при открытии по deep-link — полный набор
снимков появляется без ручного просмотра; проверка: 12/12 ходов за ~200 с.

## Урон (0.8.0, M14): журнал команд v2 + HP-дельты

Разведка (`POLYREAD_DUMP_FIELDS`) дала недостающие поля:

- `AttackCommand`: `<UnitId>` (атакующий), `<Origin>`, `<Target>` (WorldCoordinates);
- `MoveCommand`: `<UnitId>`, `<From>`, `<To>`;
- `RecoverCommand`/`DisbandCommand`/`ExplodeCommand`: `<Coordinates>`;
- `BattleResults` (переходящий объект боя): `attackDamage`, `retaliationDamage` —
  подтверждает, что готовых накопительных счётчиков урона в состоянии нет
  (`PlayerState`/`UnitState`/`PlayerRankingViewModel` проверены);
- `targetGameState.ActionStack` ПУСТ — полного журнала действий игра не хранит.

Шим пишет `commands.json` v2 (координаты/uid у перечисленных команд) и
`units: [id, owner, health, type, x, y]` (сквозной id юнита + координаты).
`actions.json` (перехват очереди анимаций с дедупликацией по отпечатку) —
только диагностика: ~30% боевых действий.

Импортёр реконструирует урон детерминированно ( `_compute_damage` ):
ходы команд выводятся из циклов `EndTurnCommand`; потеря HP юнита, по которому
в раунде были `AttackCommand`, — урон атакующих; потеря HP атакующего,
которого не били, — контратака (защитнику); исчезновение юнита без атаки и без
Disband/Explode — небоевое (посадка на корабль); смерть учитывается по
остатку HP (overkill не виден — занижение на величину добивания); лечение
в том же раунде занижает урон (флагуется в notes). Внутренняя шкала HP ×10
(100 = 10 HP в UI). Проверка на эталонном реплее (Timeless Battles, 12 ходов,
16 атак): все потери HP объяснены командами, небоевые исчезновения отсеяны,
баланс сошёлся (KOF 25.0 / Goylem 43.0 урона).
## Быстрое снятие реплея: нативная перемотка (0.10.0, эксперимент)

Задача: не ждать полного проигрывания реплея (~200 с на 12 ходов), а снять
все ходы за секунды.

### Почему нельзя «сразу в конец»

Реплей Polytopia — не запись состояний, а **начальное состояние + журнал
команд** (`targetGameState.CommandStack`): движок детерминированно пересчитывает
матч по ходу проигрывания. До проигрывания игра не знает даже финальный счёт
(проверено: в `snapshot-000` поля `end_score=0`, `resigned_turn=-1`). Мгновенно
доступен только журнал команд — его шим и так снимает сразу.

### Как работает seek-режим (POLYREAD_SEEK=1)

Разведка методов (`POLYREAD_DUMP_METHODS`) нашла в `ClientBase` нативную
перемотку: `SeekToCommandImmediate(UInt16, Action<Boolean>)` и `SkipRecap()`.
Алгоритм шима:

1. **План**: два прохода по CommandStack — маска игроков, выпускающих
   `EndTurnCommand` (включая Nature/pid 255 — бит сводится в 0x80000000), и
   индексы последних EndTurn каждого цикла (= границы ходов, та же логика,
   что в `_command_turns` импортёра).
2. **База**: `snapshot-000` пишется из `ClientBase.initialGameState` —
   детерминированно, без гонки с проигрыванием.
3. **Заморозка**: `ActionManager.StopProcessing()` на время снятия,
   `StartProcessing()` по завершении (или при отказе).
4. **Шаги**: перемотка к каждой границе; длинные прыжки дробятся ступеньками
   по `SEEK_MAX_HOP=16` команд (длинные прыжки движок применяет асинхронно и
   «проматывает» состояние к финалу — так портился цикл 11).
5. **Безопасность вызова**: перед каждым вызовом — ожидание «idle» движка
   (`targetGameStateCurrentCommand` не меняется 2 тика) и кулдаун 2 тика:
   вызов во время пересборки состояния роняет процесс. Первое обращение часто
   бросает `Exception` (движок занят) — повторяем на следующем тике.
6. **Верификация**: после перемотки поле `turn` должно быть `label-1..label`;
   если больше (финишный рывок движка промотал состояние) — перемотка назад
   (гонщик уже финишировал, обратная пересборка чистая), до 3 повторов.
   Снимок пишется с меткой цикла — полю `turn` при перемотке доверять нельзя.

Результат на эталонном реплее (12 ходов): **снятие 15–25 с вместо ~200 с**,
все 13 снимков байт-в-байт идентичны пассивному снятию (проверено 3 раза).

### Надёжность и статус

ВЫЗОВЫ методов движка из побочного потока не поддерживаются Unity — это
осознанный риск. Статистика 6 прогонов на момент написания: 3 идеальных,
1 порча последнего цикла (до верификации turn), 1 внутренний сбой с авто-
откатом на пассивный режим, 1 гибель процесса игры. Поведение при отказе:
шим размораживает проигрывание и доснимает матч пассивно; если игра погибла —
данные до сбоя сохранены, реплей нужно открыть заново.

Режим ОПЦИОНАЛЬНЫЙ (`POLYREAD_SEEK=1`), по умолчанию — пассивное снятие.

### Конфигурация без перезапуска Steam

Шим читает `~/.local/share/polytopia-analyzer/shim.env` (строки `KEY=***
применяются через setenv только если переменная не задана в окружении —
launch-опции Steam имеют приоритет).

### Мёртвые концы (не повторять)

- **Unity `Time.timeScale`**: setter `set_timeScale` вырезан стриппингом IL2CPP
  в текущей сборке игры (в метаданных только getter) — ускорение времени
  недоступно; код в шиме оставлен на случай будущих сборок.
- **`targetGameStateCurrentCommand` как критерий готовности**: поле отслеживает
  покадровое применение команд (лимит `MAX_STATE_UPDATES_PER_FRAME`) и сильно
  запаздывает — пригодно только как индикатор занятости движка.
- **SkipRecap при снятии**: снимает анимационное торможение, и движок гонит
  журнал вперёд быстрее перемоток — состояние уезжает к финалу. Не зовём.
- **Прямой запуск с аргументом `opengame?id=…`**: реплей открывается только
  через deep-link Steam (`steam://run/874390//opengame?id=…`).
